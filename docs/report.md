# 报告怎么读：一页看懂 `attribute` 的输出

`pcause attribute` 会写两份报告（Markdown + 独立 HTML），`--json-out` 还会给一份机器可读结果。三份内容同源，这一页只讲「怎么读」。

## 1. 顶部：先确认实验条件

| 行 | 你要确认什么 |
| --- | --- |
| 归因对象（`--kind`） | prompt / system / agent。它决定判定维度与「假设可信度」，不同 kind 的结论不要横向比 |
| 每探针采样 | 采样次数。**1 次 = 没有噪声地板**，结论只能当弱证据 |
| 噪声地板 | 同一提示词自己跟自己比的变化率。越高说明模型越随机 |
| 判定口径 | 决定性 ≥50%、部分影响 ≥20%、无影响 <20%（校正后影响） |
| 预算 | `--max-calls` 是模型请求次数，不是金额 |

看到「⚠ 稳定性警告」时，先别读结论：它表示采样不足、噪声过高或预算耗尽，此时百分比会剧烈抖动。

## 2. 排行表：三个数字的关系

```text
■  h2  决定性   100%（原始 100%）
□  h3  无影响     0%（原始   0%）
```

- **原始变化率**：把「新提示词输出」和「回退这一块之后的输出」交叉配对，判定为 changed 的比例。
- **噪声地板**：同一提示词重复采样之间被判 changed 的比例。模型自己就会抖，这部分不算你的功劳。
- **校正后影响** = (原始变化率 − 噪声地板) / (1 − 噪声地板)，负数截断为 0。报告默认用它来给判定。

因此：原始 33% + 噪声 33% → 校正后 0%（这个块其实什么也没影响）。**只看原始百分比会把噪声认成功劳。**

## 3. 三个最容易误读的数字

1. **0% ≠ 没测**。预算耗尽或提前停止的块会标 `unmeasured` / 「采样不足，未测完」——那是「不知道」，不是「无影响」。
2. **第二意见 12/12 ≠ 结论正确**。它只说明另一个异构模型对同一批配对给出了相同判定；两个模型可以一起错（例如 prompt 本身就有歧义）。
3. **影响百分比 ≠ 重要性**。它衡量「这一块改动改变了多少比例的探针行为」，不衡量这个行为对业务有多重要。一条格式要求可以是 100%，一条业务规则也可能只有 33%。

## 4. 证据区：不要只看结论

每个块后面会附「探针输入 + 新提示词输出 vs 回退后的输出」的代表性配对。判定器可能犯错，证据不会骗人：

- 如果两边输出实质相同，judge 却判了 changed，说明判定口径或探针选得不对；
- 如果回退后的输出直接报错/为空，那多半是这一块改动在支撑某个前置约束，别急着删。

## 5. 建议怎么用

- **「可删」只表示「在你这批探针上没测出行为变化」**，删之前先用真实流量抽一批探针复测；
- 想保留但不确定的块，把它拆成更小的改动再测（hunk 越粗，归因越糊）；
- 想比较两次改动的结论，用 `pcause compare`（见 [compare.md](compare.md)），不要肉眼对表。

## 6. HTML 与 JSON

- **HTML**：给人看的独立页面，排行、进度条、证据折叠，适合贴给同事或存档。
- **JSON**（`--json-out` 或 `pcause schema`）：给 CI / 看板用，字段契约见 `schema/attribution.schema.json`；`--fail-on decisive|partial` 可做门禁（退出码 2）。
- **Markdown**：给代码仓库/PR 用，便于 diff。

同一份归因的 JSON 与报告不会互相矛盾；如果看到矛盾，优先信 JSON（它经过 schema 校验）。
